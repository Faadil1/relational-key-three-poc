# RELATIONAL KEY — Astra V1 ↔ V2 Evaluation Brief

## Purpose

Evaluate the current RELATIONAL KEY V2 against the frozen/stable V1 and propose the strongest bounded improvements that preserve the original product scope.

This is **not** a request to redesign the project into a generic 3D gallery, an AI-dashboard aesthetic, a dark-blue/black SaaS shell, or a decorative archive showcase.

## Original product scope — non-negotiable

**THE RELATIONAL PAIR REMAINS THE PRODUCT.**

Primary causal model:

`PAIR MEMBER → RELATION → OTHER MEMBER RESPONSE`

A family succeeds only when the memorable moment belongs to the **relationship between two distinct members**. If either member can be removed without materially breaking the memorable moment, the concept has drifted.

Additional frozen laws:

- Expansion must deepen the relation, not replace it.
- Technology serves the relational mechanism.
- Archive evidence must change the mechanism, not decorate it.
- Cultural/material specificity must be legible without unsupported historical claims.
- Mobile, reduced-motion, keyboard and runtime quality are release criteria, not optional polish.

## What V2 is trying to improve over V1

V2 was created to preserve the relational clarity of V1 while increasing:

1. interaction quality;
2. memorability;
3. mechanism-specific identity;
4. archive-derived specificity;
5. collection-level coherence across 24 families;
6. technical scaling through one active WebGL canvas and lazy family chunks.

Promotion criteria used throughout V2:

- relational clarity >= V1;
- interaction quality > V1;
- memorability > V1;
- truth integrity = V1;
- accessibility/mobile >= V1 within tested scope;
- runtime acceptable.

### 1. Product-level comparison

Determine whether V2 genuinely improves the original concept or merely adds technical/visual sophistication.

For each conclusion, answer:

- Is the pair still the product?
- Is the relation perceptually obvious before explanatory text?
- Does interaction reveal a causal dependency between A and B?
- Is the memorable moment owned by the pair rather than one object?
- Does the collection feel intentionally authored rather than AI-generated or template-driven?

### 3. Portfolio / presentation comparison

- evidence that the interactions were validated rather than generated decoratively;
- technical system quality without overwhelming the creative/product story.

## Improvement rules

Astra may recommend substantial improvements, but proposals should be ranked by value and risk.

Preferred order:

1. improvements that make the relation legible faster;
2. improvements that make archive/material identity more native;
3. improvements that make the response more memorable while remaining pair-owned;
4. improvements to composition, hierarchy, pacing and interaction feedback;
5. improvements to accessibility/mobile/runtime;
6. only then broader visual-system changes.

Avoid:

- dark navy / black AI-product clichés as a default redesign language;
- neon gradients, glass cards, generic glowing orbs, random particles, fake HUDs;
- replacing pair-native mechanisms with cinematic spectacle;
- decorative historical imagery that is not causally relevant;
- flattening the 24 families into one repeated interaction template;
- unsupported cultural/historical claims;
- degrading keyboard, mobile or reduced-motion behavior;
- introducing many simultaneous WebGL canvases.
